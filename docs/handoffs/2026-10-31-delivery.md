### What was done

- **Pins from the webhook.** `type: "location"` gives `latitude`/`longitude` (numbers or numeric strings, in
  range; else dropped). Kind stays `other`; the pin lives in new nullable `inbound_messages.latitude_e6` and
  `longitude_e6` (INTEGER millionths of a degree: no floats in D1). The pin's map name and address aren't stored.
- **Reading.** The model sees "ubicacion compartida", never coordinates. If it gives no `fulfillment` for a burst
  with a pin, code adds one (mode unknown). A burst of only pins makes no model call.
- **`customer_places`** (0017): `business_id`, composite FK to `customers (business_id, id)`, `UNIQUE (business_id,
  id)`, `UNIQUE (business_id, order_id)`, place text (as written, ≤300) and/or pin. Saved only when a delivery
  order is confirmed (`order_confirmed` in the job's batch): new place = one row per order (upsert that never
  moves a row to another customer); an accepted saved place is marked used. Pickup and cancelled orders save
  nothing. Customer deletion deletes the rows and clears pins on their messages.
- **Saved place offered, never applied.** The handler reads the newest used place and passes it to the engine as
  `savedPlace`. The reply: "¿Te lo llevamos al mismo lugar de siempre?" + "La vez pasada te lo llevamos a: …" (or
  "La vez pasada nos mandaste tu ubicación.") + "Respondé Sí u Otro lugar.", buttons Sí / Otro lugar. A tap is
  its own step (operation key = button ID); typed answers go through perception.
- **Readback:** "Te lo llevamos a: <as written>." or "Te lo llevamos a la ubicación que nos mandaste."; a fee line
  only when `fee > 0` (always null today: no store settings).
- **Pretend engine** (memory and D1, same code): every order still asks `pickup_or_delivery`; pickup drops any
  place; a pin or place text makes it a delivery there; with no place it asks `same_place` when a saved place exists
  (once per order unless declined), else `delivery_place`; `accept_saved_place` only for the context's place
  (`not_found` otherwise); `decline_saved_place` asks where; a `clarification` to `same_place` is a yes only via
  `isYes`, to `delivery_place` it's the place. Old D1 snapshots import with `declinedSavedPlace: false`.

### Risks and open questions

- Saved places live in our table, keyed by the engine's order ID (no FK: orders are hers). If the engine wants
  places in its own records too, we agree who owns them.
- `isYes` is a short word list in the pretend engine; the real engine decides its own reading of a yes.
- Place text is shown capped at 60 characters in replies (stored up to 300).
- The D1 pretend snapshot now also holds place text and pins; customer deletion doesn't purge the snapshot (known
  risk from the pretend-online handoff).
- Migration numbering: 0017 only here (0018 is another lane's).
