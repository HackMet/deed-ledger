## Handoff: planner-path latency (reasoning effort, prompt cache)

- Agent and branch: Claude Code, `claude/latency` (based on `claude/agentic`) in `hackathon-claude-latency`. Nothing
  committed.
- Objective: each customer burst on the planner path makes two Muse Spark calls (reader, then planner). A live check
  measured 28–42 s end to end, against a QA bar of under 10 s typical. Lower each call's reasoning effort where it
  stays correct, make the fixed instructions cache-friendly, measure, and set the defaults.
- References: `PLANNER-CONTRACT.md` §1 (two-call budget) and §9 unknowns 1 (two-call latency), 2 (effort control) and
  6 (cost per message); D-45. Meta's Chat Completions docs (checked Nov 2): `reasoning_effort` takes `minimal`, `low`,
  `medium`, `high`, `xhigh` (and `max` on muse-spark-1.3), and `none` is refused with HTTP 400 on Muse Spark. Without
  it the model picks its own effort. `max_tokens` caps reasoning plus output together. `prompt_cache_key` groups
  requests; `prompt_cache_retention` takes `in_memory` or `24h`.

### What was done

- **Per-call settings.** `ModelRequest` carries an optional `reasoningEffort`, `promptCacheKey` and
  `promptCacheRetention`. `MuseSparkProvider` sends them as `reasoning_effort`, `prompt_cache_key` and
  `prompt_cache_retention`, but only values Meta lists, so `none` or a typo never reaches the wire. Each call site's
  effort and retention come from `MeteredCallDeps.settings`, set in composition from the Worker's variables:
  - `READER_REASONING_EFFORT` and `PLANNER_REASONING_EFFORT` take one of Meta's efforts, or `default` to send none.
    Blank, `none` or anything else gives the measured default: on the planner path, reader `low` and planner
    `minimal`.
  - The classic path's reader keeps the model's own effort unless the variable is set. Its prompt (with catalog
    picks) wasn't measured, and classic is still the production default.
  - The console's reader (Anotar) gets no settings.
  - `PROMPT_CACHE_RETENTION` takes `in_memory` or `24h`; blank sends none.
  - Simulator switches: `--reader-effort`, `--planner-effort`, `--cache-retention`.
- **Spend cap unchanged.** The reservation is still the input bound plus the full output cap. `max_tokens` caps
  reasoning plus output at every effort, so the bound holds whatever the effort. A lower effort only settles lower; it
  never reserves more. A test checks that four efforts reserve the same amount and settle the actual usage.
- **Cache-friendly instructions.** The planner's system prompt was already a pure join of the two instruction files.
  A test now checks that it is the same bytes across stores and messages and carries no store or message data. The
  cache key is the instruction version (`planner:base@<hash>+mercadito@<hash>`). The reader's key is
  `reader:<prompt version>` (`reader:order-v2-nopick`, `reader:order-v2`, `reader:console-v1`). Keys never name a
  store or a customer.
- **Usage in the logs.** `*.model_call` lines now carry `effort`, `inputTokens`, `cachedTokens`, `outputTokens` and
  `reasoningTokens`. These are counts only; `LogFields` gained the five keys.

### How it was measured

Simulator with `--ai --store --planner --port 8794`, QA store seeded (`npm run qa -- --seed`). A driver (outside the
repo) sent a fixed set of 4 customer messages per combination, each from a new customer, and waited for the job to
finish before sending the next:

1. the photo `lista-pedido.jpg` (5 items with counts; expected 3 × Arroz, 2 × Clover 1 L, 1 × Huevos, 5 × Consomé,
   2 × Jabón, total L 379, then the pickup-or-delivery question);
2. the photo `lista-once.jpg` (11 items, no counts);
3. "buenas, me manda platanos, una piña, salsa de tomate y 2 libras de arroz. lo paso a traer";
4. "6 platanos" as the follow-up from the same customer.

Sources of each number:

- Per-call latency and tokens come from the Worker's `*.model_call` log lines (server side).
- "Receipt→reply" is `job_finished_at_ms − received_at_ms` from D1.
- Outcomes come from the pretend engine's order (lines, quantities, total) and the planner's logged move and ask
  kind, checked against the replies in the outbox.
- Costs are at list price ($1.25 / $4.25 per million tokens), counting cached input at full price, so they are an

Facts from the runs:

- Latency follows output tokens. The reader produced a median of ~130 output tokens/s and the planner ~107/s, so
  every 100 reasoning tokens costs about 0.8–0.9 s. The model's own effort reasoned 1,000–4,100 tokens per call.
- Receipt→reply is the model time plus a steady **~4.3 s**: the 3 s burst settle (`SETTLE_MS`), the queue's
  whole-second delay, and about 0.3 s of our own work.
- Prompt caching works without the retention setting. Most calls after the first hit 1,777–5,361 cached input tokens.
  `prompt_cache_retention: "in_memory"` was accepted (HTTP 200) and changed nothing visible. `24h` wasn't tried.

### Quality risk that remains

- **Reader at `low`:** the reader's evidence rules were proven at the model's own effort (8.65/10, 0 truth fails).
  Here only 10 reader calls on 4 synthetic inputs were checked. Not covered: injected instructions, voice
  transcripts with spoken corrections (E1-16/17), prices per box versus total (E1-04), long or messy handwriting.
  Lane L2's eval must rerun at these efforts before `CONVERSATION=planner` becomes the default.
- **Planner at `minimal`:** which items get a suggested 1 (decision 2A) varied on the 11-item list: 4, 4, 5, 2 and 3
  items across runs. The question kind never changed. The two runs with the model's own reader effort both suggested
  the same 4. With so few runs, whether this comes from the reader's effort or from sampling is unknown. The
  suggestions are shown openly and confirmed by the customer, and code validates every op, so this is inconsistency,
  not a truth failure.
- **Cost:** cached input is counted at full price, so costs are an upper bound. Meta's cached-token price: unknown.

### Next lever (described, not built)

**A one-call path for text-only bursts.** Retrieval would run on the burst's own words before any model call: the
same all-words / any-word catalog search, over the text's word runs instead of the reader's item names. One call would
then return both the reading (observations with evidence, validated exactly as today) and the turn proposal, as one
strict schema. Photos and voice notes keep the two calls.

- Expected gain, from the measured rates: one prompt instead of two, and one reasoning phase. Model time on text would
  drop from ~9 s to roughly 5–6 s, about 9.5–10.5 s receipt→reply. Estimated, not measured.
- Risks: retrieval on raw text offers candidates for words that aren't items, which makes the input longer. It also
  mixes "what was said" with "what to do", which the contract's §1 keeps apart on purpose.

Two smaller levers stack with it, and each needs its owner's call:

- A shorter burst settle for a lone text message. Today it is ~4 s before the job starts; 1.5 s would save about 2 s
  per message, but a customer typing fast would get split bursts.
- A shorter reader output. Each item's words are written three times (`text`, `name`, evidence quote): about 300–900
  visible tokens, 2.5–7 s at the measured rate.

Long photo lists will stay above 10 s with any of these: the 11-item reading alone is ~900 visible tokens.
