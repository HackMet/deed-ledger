### What was done

- **Wire format.** Separate from the contract on purpose: evidence is `{ message, quote, box }`, and code finds the
  span and picks the source from the message's type (text, transcript, image). Models count characters badly.
  Lines carry `pick` (a catalog label or null). Edits are flat. `fulfillment.mode` uses `"unknown"` for null.
- **Checks.** A response that doesn't fit the schema is refused whole (`invalid_output`): staff kinds from a
  customer, extra keys such as a product ID, wrong types. Inside a valid response nothing is repaired: a non-decimal
  quantity becomes null plus `illegible` on that line; a line whose evidence isn't in the burst (quote not found,
  message out of range, box outside 0–1) is dropped and replaced by an `illegible` issue, with the model's issues
  renumbered; refs not among the open order's labels become null; picks not among supplied labels are ignored;
  money must be `isCentavos`; staff kinds are refused again after mapping (`isCustomerKind`); an empty reading is
  `other`; a `set_quantity` with no affirmed figure becomes an issue, not an edit.
- **Security.** One fixed system prompt per audience. Context and messages go only in the user turn, each message
  `JSON.stringify`-quoted. `*-contributor` model IDs throw at construction. With `MODEL_API_KEY` blank the provider
  refuses before the network. Logs carry `businessId`, counts and codes only. A schema mismatch logs `"schema"`,
  not the path, because an unexpected key is model-written text.
- **Spend cap.** `model_spend (business_id, day, micro_usd, calls)`. Reserving is one upsert whose insert and
  update both check the cap. D1 runs statements one at a time, so concurrent reservations can't both pass. Before
  each call the reader reserves an estimate (4,500 input tokens + text/3 + 1,600 per photo, plus 4,000 output
  tokens; about $0.023). After the call it settles to the actual usage: 0 when the request was refused, the
  estimate when the spend is unknown. Default cap US$2 per store per day.
- **Matching.** Code first: barcode (8–14 digits), exact name, known alias, each needing exactly one product.
  Several candidates means no match. The model's `pick` applies only to lines code couldn't match, and only when
  it is a label code supplied (up to 200 products, `P1…`). It comes back as `labelMatches`, separate from
  `LineMatch` (see contract questions).

### Not done, risks, open questions

- **Authored vs live fixtures.** Only `live.ts` holds real model output. The contract and E1 fixtures are written
  by hand in the wire format. They pin our mapping and checks, not the model's accuracy. Measuring the model on
  photos and E1 is #28.
- **No `LIVE_TESTS=1` path.** `test/setup.ts` fails the run if any key binding is non-empty, so a live test inside
  workerd needs a deliberate change to the test config. The live check ran as a standalone script.
- **Not wired.** Nothing calls `BurstReader` yet: the job handler is #17/#26 (photo bytes from R2, transcripts from
  #27). The catalog comes from the caller; no catalog repository exists yet.
- **Latency.** About 7 s per call, mostly reasoning tokens (1,300–1,600). Worth watching against reply timing.
- **Store day** is fixed at UTC−6 (Honduras, no DST), not stored per store.
- **E1 mapping.** Expenses, debt payments, owner questions and ledger corrections have no console kind after the
  pivot, so they read as `other`.
- **Contract questions** (contract files not changed):
  1. `LineMatch.how` has no value for a model pick among code-supplied labels. Add `"label_pick"`, or keep
     `labelMatches` separate?
  2. `PerceptionContext` has no catalog labels. Defined locally as `ReadingContext.catalogLabels`.
  3. `ObservationIssue.code` has no "unclear quantity" or "couldn't place this line" code. Both map to `illegible`
     for now ("ocho o nueve", invalid evidence). Add `ambiguous_quantity` and `unplaced`?
  4. A `set_quantity` with no affirmed number can't be expressed (`quantity` is non-null). It becomes an issue.
  5. `setup_card.barcode` comes from the scanner; the reader sets it null and the console has to fill it.
